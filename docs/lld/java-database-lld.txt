Design note:
DatabaseServer owns StorageEngine and NetworkModule lifecycles; uses QueryProcessor (no lifecycle).
NetworkModule owns RequestHandler.
Wire protocol v1: request frame = plain UTF-8 SQL; response frame = JSON WireResponse (see docs/protocol/wire-protocol.md). QueryProcessor returns QueryResult; DefaultRequestHandler calls result.toWireResponse() (Ok, Error, or ResultSet+Done). executeText() / toResponse() remain for tests and logging.
DefaultQueryProcessor owns QueryLexer, QueryParser, and QueryPlanner; builds DefaultQueryAnalyser and QueryDispatcher on first catalog use from StorageEngine managers (requires start()). Uses StorageEngine (does not own its lifecycle).
execute() lexes, parses, analyses, plans, then runs plans through QueryDispatcher. Implicit DDL: TransactionManager.runInTransaction → LockManager.runExclusiveCatalog → WAL append (txnId) → CatalogManager → COMMIT+flush. Explicit BEGIN: TransactionControlExecutor holds lock, defer catalog persist until COMMIT. CHECKPOINT: CheckpointExecutor → exclusive catalog → WALManager.checkpoint() (update wal.checkpoint, append CHECKPOINT to wal.log — append-only); refused inside explicit txn. Background CheckpointScheduler plugs one CheckpointStrategy (timeout or wal_size) when CHECKPOINT_ENABLED. DESCRIBE / SHOW DATABASES / SHOW TABLES read CatalogManager only (no txn, lock, or WAL). Table names are database.table. SELECT / INSERT / UPDATE / DELETE are analysed and planned (table vs index scan from catalog IndexMetadata); VolcanoExecutor compiles plans into pull operators over InMemoryTableStore (INDEX_SCAN = SeqScan until B+Tree). SeqScan (SELECT) takes row S-lock then re-reads via TableStore.findByRowId — heap scan snapshot at open() can be stale after lock wait. UPDATE/DELETE use WriteScanPrefilter: pre-lock Filter only for WHERE id = literal; otherwise UpdateOperator/DeleteOperator lock each heap row, re-read, then evaluate WHERE (unlock X if row gone or WHERE fails and lock was taken this statement). Empty SELECT returns a result set with zero rows (executeText still "OK"). Rows are RAM-only — restart keeps catalog, SELECT is empty. DROP TABLE/DATABASE clears store heaps via CommandExecutor. VectorizedExecutor / BatchExecutor exist as stubs but are not registered. Unresolved plans still echo OK <query>.
Lex/parse errors become the response via LexException/ParseException.toResponse() (exact 0-based index).
Lexer types live under com.example.database.processor.lexer (unchanged names).
Parser types live under com.example.database.processor.parser.
DefaultQueryParser dispatches via ParserRegistry; statement parsers own grammar; AST holds structure.
DatabaseServer passes QueryProcessor into NetworkModule; NetworkModule assigns it to RequestHandler.
RequestHandler bridges network and query processor (JSON wire responses via JsonWireResponse).
java.net.Socket classes stay inside the TCP implementations.
database-client is a separate Maven module: DatabaseClient REPL over the same length-prefixed TCP framing; parses JSON with client.wire.WireResponseJson, prints via ResponsePrinter. Not wired from Main/StorageEngine.

Catalog (Phase 1.1–1.3):
CatalogManager is a StorageEngine submodule and owns CatalogStore.
DefaultStorageEngine constructs PhysicalStorage, DefaultCatalogManager, DefaultWALManager, DefaultUndoManager, DefaultTransactionManager(wal, undo), DefaultLockManager (DETECT_RESOLVE), CheckpointScheduler (strategy from ServerEnvironment), UndoableTableStore over InMemoryTableStore, and DefaultBufferPool. start() loads catalog, replays WAL (COMMIT-gated; merges wal.checkpoint maxTxnId), seeds next txnId, starts scheduler if enabled. stop() flushes dirty buffer-pool pages then stops the scheduler.
start() calls catalogManager.load() — the engine does not touch catalog files.
createTable assigns ids and writes data/<db>/<table>/catalog.json. Restart: new engine, start, getTable("shop","users").
CREATE DATABASE creates data/<name>/; DROP DATABASE removes an empty directory (fails if tables remain). load() lists those directories and per-table catalogs.
CREATE TABLE via SQL: CREATE DATABASE shop then CREATE TABLE shop.users (...); processor.execute then a new StorageEngine on the same dir; getTable is the same; a second CREATE is an error.
DROP TABLE shop.users deletes the table catalog file and empty table folder.
Root data/catalog.json is not read or written.
CatalogStore owns JSON and path layout; PhysicalStorage owns bytes.

PhysicalStorage (Phase 1.2):
PhysicalStorage is a StorageEngine submodule. DefaultPhysicalStorage is filesystem bytes under DataDirectory.
No page read/write APIs. Catalog JSON is opaque bytes at this layer.

Page layout (Phase 2):
HeapPage / RowCodec / Rid / RidMap live under storage.page. Pure codecs over byte[pageSize]; default 16 KiB.
Header (24 B) + slot directory (4 B × slotCount) + free [lower,upper) + packed row payloads from the high end.
rowId remains the lock/undo key; Rid=(pageId,slotId) is the heap address. InMemoryRidMap is RAM-only.
TableStore is still InMemoryTableStore. BufferPool.newPage writes an empty HeapPage image when extending a file.

BufferPool (Phase 3):
DefaultBufferPool is constructed by DefaultStorageEngine; pin/unpin, per-frame S/X latch, dirty bit, clock eviction.
Page key is (file, pageId). Phase 3 never evicts dirty frames (no-steal until DML WAL); flush/flushAll write them.
stop() calls flushAll(). Catalog JSON and wal.log stay off the pool. DML does not use the pool until FileTableStore.
